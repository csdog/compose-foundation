# Compose Foundation 代码审查与清理计划

实际审查状态、发现、验证结果和提交记录见 [代码审查进度](code-review-progress.md)。每完成一个审查项后更新该文件。

## 目标与范围

以 `95c932b6` 为审查基线，优先清理近期 Web 对齐改动中的硬编码、重复逻辑和职责混杂。第一轮覆盖 `:shadcn:core` 的 Select、Toast、共享弹层和各自的 Web 适配。第二轮将已验证的审查方法用于 Slider、Sheet、Toggle，以及 app 目录页的浏览器滚动和导航。先盘点目标文件已有的本地改动。与他人改动重叠的文件可以记录发现，修复等对应改动整合后再做。

清理时保留公开 API、默认行为和已有主题差异。发现真实缺陷时，单独写清复现条件和期望行为，再做有针对性的修复。

| 2. 治理硬编码 | Select 的弹层几何与滚动、Toast 的时长与手势阈值 | 共享视觉值复用现有主题 token。局部行为参数用能表达规则和单位的名称。密度、布局方向、可用宽高从运行时读取。 | 原有默认值和视觉对齐保持一致。测试覆盖分数密度、窄窗口、RTL 或阈值边界中与该修改相关的情形。 |
| 3. 拆清职责 | `SelectContent`、`NovaToastViewport` | 让渲染层处理组合与布局，让一个明确的所有者负责同一份可变状态。把可独立验证的几何计算与决策留在纯函数中。重点检查队列更新、计时暂停和焦点归还的副作用边界。 | 同一个状态只有一个明确的写入入口。每次提取都能指出减少了哪项重复计算、状态同步或调用者负担。 |

## 硬编码的判定

- **主题视觉值**。先找项目已有的颜色、圆角、间距和动画 token。对齐规范中有来源、仅由一个组件使用的值可以留在组件的样式定义中。
- **行为规则**。锚点安全边距、手势阈值和计时等值需要有明确的所有者和单位。只有现有调用者需要不同策略时，才开放配置。
- **环境数据**。窗口尺寸、密度、布局方向、减少动态效果偏好和平台能力从对应运行时读取。审查计算链条中的 `dp`、窗口像素与 CSS 像素转换。
- **普通字面量**。`0`、`1`、枚举映射、示例数据和测试期望值在就地可读时保留。单纯为数字起名没有必要。

审查示例和生成代码时，先确认唯一的源文件。例如 Toggle 的示例代码由目录预览的 Kotlin 源生成，改动后运行 `python3 scripts/generate_toggle_recipe_code.py --check` 核查一致性。

## 验证与完成标准

- 行为修复先验证原实现能复现，再验证修复有效。结构调整复跑受影响的现有用例，优先用原有公开入口验证行为。第一批从 `SelectPopupGrowth*Test`、`ToastManagerParityTest` 和 `ToastBehaviorParityTest` 开始。
- 跑触及模块的 ktlint 和 Detekt。复杂度告警用于定位问题，修复应减少职责混杂或依赖数量。既有告警单独记录，保留现有规则阈值。
- 改动视觉、布局或动画时，按 [视觉测试说明](visual-testing.md) 验证对应快照。变更 Web 适配时编译受影响的 JS/Wasm 目标，用真实浏览器复核键盘、触摸、主题和 RTL 中受影响的场景。快照更新需要有明确的预期视觉差异。
- 每项发现都记录为已修复、有证据保留，或因缺少基线、存在工作区重叠、涉及公开契约变更而延后。交付时列出提交、验证结果和待处理项。

首批验证使用以下 Gradle 任务，按实际改动追加截图或 Web 验证。

```sh
./gradlew :shadcn:core:jvmTest --tests '*SelectPopupGrowth*Test' \
  --tests '*ToastManagerParityTest' --tests '*ToastBehaviorParityTest'
./gradlew :shadcn:core:ktlintCheck :shadcn:core:detekt
```
